# HireMe Flutter Constitution

## Migration Mode

**Mode**: MAINTENANCE

Justification: HireMe is an active Flutter GetX project with established architecture, Firebase/Supabase integration, and dual-role authentication. This constitution documents existing practices and governance rules to ensure consistent development across team members and future enhancements.

## Core Principles

### I. GetX State Management Purity
All controllers inherit from `GetxController` and live in `app/modules/{role}/{feature}/` with explicit bindings. Controllers are registered via `Binding` classes (never direct `Get.put` in UI). Model layer and Service layer are decoupled from UI; services are registered in `main.dart` or feature bindings via `Get.putAsync`. Lazy-loading controllers use `Get.lazyPut` when the controller supports deferred initialization.

### II. Firestore Merge Semantics (NON-NEGOTIABLE)
Every Firestore write MUST use `SetOptions(merge: true)` to prevent data loss. Plain `set()` without merge overwrites entire documents and is forbidden. Rationale: Concurrent writes from mobile clients and Cloud Functions must not clobber unrelated fields.

### III. Firebase + Supabase Dual-Backend
Firebase handles real-time auth, Firestore (collections + RTDB), and Cloud Messaging (FCM). Supabase handles authentication with PKCE flow (`AuthFlowType.pkce`, `autoRefreshToken: true`), file storage (all uploads go through Supabase Storage, not Firebase Storage), and relational data if needed. Token cleanup on logout is MANDATORY: delete FCM token → `deleteToken()` → `clearAuthSession()` → `signOut()` (skipping any step leaks FCM tokens).

### IV. Manual Testing Only (No Mockito/Mocktail)
All tests use manual fakes (repository/service mocks written inline). Mockito, Mocktail, and other mocking frameworks are forbidden. Controller tests must call `Get.reset()` in `tearDown` (and `setUp` if setUp registers any GetX controller) to clear GetX state. No Firebase/Supabase initialization needed in tests.

### V. Notification Data Routing & Badge Integrity
Notification data types are `chat_message`, `application_update`, or `new_application`. Routes are determined by `NotificationService._navigateFromData` (lines 204–230). Stream subscriptions MUST include `onError` handler that resets badge count to 0; omitting the handler allows a stream error to permanently break the badge. Notification badges backed by `notification_count` observable.

### VI. Modular Feature-First Architecture
Features are organized under `app/modules/{role}/{feature}/` with role-scoped hierarchy (auth, company, job_seeker, profile, shared). Each feature owns its controller, bindings, views, and local models. Shared widgets live in `core/widgets/`; shared utilities in `core/utils/`. Codegen (e.g., `lib/core/utils/app_assets.dart`) is auto-generated and never edited manually.

### VII. Route Guards & Role-Based Access
Protected routes use `RoleGuardMiddleware`. Public routes (`job_seeker_search_jobs`, `pdf_viewer`, `company_map`) have no middleware by design. All route constants are imported from `app/routes/app_pages.dart` (Routes.* namespace); `app_routes.dart` is `part of` the same file and never imported directly.

### VIII. Configuration & Secrets
`.env` must contain `SUPABASE_URL` and `SUPABASE_ANON_KEY`. `firebase_options.dart` is generated by `flutterfire configure` and never edited manually. Secrets/config files (`lib/firebase_options.dart`, `android/app/google-services.json`, `.env`) are denied in `opencode.json` and locked from editing. All three must never be committed with real credentials.

## Development Workflow

### Build & Test Commands

```bash
flutter pub get
flutter analyze --no-fatal-infos --no-fatal-warnings   # matches CI exactly
flutter test --no-pub                                   # matches CI; use --no-pub locally if dependencies stable
flutter test test/<file>.dart                           # single test file
flutter run                                              # debug build
flutter build apk --release                             # release APK
```

### CI Pipeline (GitHub Actions, `.github/workflows/flutter.yml`)

1. `pub get` → `analyze` → `test --no-pub` → `build apk --release` → Firebase App Distribution
2. All steps run sequentially; failure at any step blocks subsequent steps
3. Build output: APK to Firebase App Distribution for QA

### Cloud Functions Deployment

Source: `functions/index.js` (6 v2 handlers on Node.js 20)
- **Event-driven**: `onNewApplication`, `onApplicationAccepted`, `onApplicationRejected`, `onNewChatMessage`
- **Callable**: `rankCandidates`, `analyzeCv` (use Groq SDK via `GROQ_API_KEY` secret + Google Document AI OCR)

```bash
firebase deploy --only database     # RTDB rules
firebase deploy --only functions    # Cloud Functions
firebase deploy --only firestore:indexes   # Firestore indexes
```

### Code Review & Merge Workflow

All PRs must pass:
1. Static analysis (`flutter analyze`) without warnings
2. All unit tests passing (`flutter test`)
3. Code review checklist (see `flutter-pr` skill guidance)
4. Architecture consistency (GetX bindings, Firestore merge, routing guards)

Merge squashing is allowed if commit history is purely fixup/wip; otherwise preserve individual commits.

## Architecture Patterns & Gotchas

### DistanceMixin Usage
`DistanceMixin` (lib/app/modules/job_seeker/shared/distance_mixin.dart`) provides `userPosition`, `jobDistances`, `getDistanceToCompany()`, `updateJobDistancesFrom()` to any controller. Used by `JobSeekerDashboardController`, `JobSeekerSearchJobsController`, `JobsMapController`. Distance sort only activates when `userPosition.value != null`; jobs with null distance sort last.

### Maps & Marker Interactions
`GoogleMap` widget does NOT expose `onMarkerTapped` / `onInfoWindowTapped` callbacks. Use `Marker.onTap` or `InfoWindow.onTap` instead. `JobsMapController` is registered via `MainWrapperBinding` (not its own separate binding) because the map lives inside IndexedStack.

### Bottom Navigation (Job Seeker)
IndexedStack order: Profile (0), Chat (1), Dashboard (2), My Apps (3), Map (4). `MainWrapperController.currentIndex` defaults to 2. `JobSeekerSavedJobsController` is `lazyPut` in BOTH `MainWrapperBinding` and `JobSeekerMyApplicationsBinding` (safe due to GetX deduplication).

### MyApplications Tabs
5 tabs: All, Pending, Accepted, Rejected, Saved Jobs. Saved Jobs reuses `JobSeekerSavedJobsController` with shared `JobCardWidget`.

### Geocoding
`geocoding` package used only in `company_map_controller.dart` for reverse geocoding. Not used in job-seeker controllers.

## Governance

### Constitution Authority
This Constitution supersedes all other practices and is the source of truth for development principles, tech stack constraints, and quality expectations. Deviations require documented exceptions and principal team approval.

### Amendment Procedure
1. Propose amendment with rationale (principle change, new constraint, clarification, or version bump).
2. Document old vs. new language and version change (MAJOR.MINOR.PATCH).
3. Update affected downstream files: feature specs, implementation plans, task templates, skill guidance.
4. Commit with message: `docs: amend constitution to vX.Y.Z (reason)`
5. Include Sync Impact Report in commit body listing all amended files.

### Versioning Policy
- **MAJOR**: Backward-incompatible principle removals or significant redefinitions (e.g., switching from Firestore to relational DB, replacing GetX).
- **MINOR**: New principle added, existing principle materially expanded, or new architectural constraint.
- **PATCH**: Clarifications, typo fixes, wording refinements, non-semantic updates.

### Compliance & Review
- All PRs must verify architecture compliance (GetX bindings, Firestore merge, routing guards, notification patterns).
- Complexity or principle violations must be justified inline or rejected.
- Runtime guidance: See `AGENTS.md` for gotchas, patterns, and exact command syntax.

### Quality Gates
- Analyze must pass with zero violations (`flutter analyze --no-fatal-infos --no-fatal-warnings`).
- All unit tests must pass; no pending tests allowed.
- No Firebase credentials, secrets, or `.env` keys in Git history.
- New features must follow GetX architecture (controller + binding + routes) and include unit tests with manual fakes.
